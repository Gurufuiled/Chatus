# Step 5. Rust для локального поиска и индексации

## Цель

Подготовить быстрый local search/index engine для больших чатов и derived views, не завязываясь на удаленный full-text backend.

## Почему это имеет смысл

У нас уже есть:

- поиск по чату;
- профильные вкладки `Медиа / Файлы / Голосовые / Ссылки`;
- локальная история в SQLite.

Пока объемы небольшие, JS/SQLite хватает. Но при росте истории:

- поиск станет тяжелее;
- derived tabs будут дороже считаться;
- фильтрация и индексация начнут есть время на устройстве.

Rust здесь хорош как local indexing engine.

## Что именно переносить

### Первая волна

1. Индекс текста сообщений
2. Индекс ссылок
3. Индекс media/file markers

### Вторая волна

4. Быстрый search API по локальной базе
5. Подсветка совпадений
6. Ranking/scoring при поиске

## Какие текущие зоны проекта это затронет

- `mobile/src/screens/ChatScreen.tsx`
- `mobile/src/components/ChatTopBanners.tsx`
- `mobile/src/screens/ChatProfileScreen.tsx`
- `mobile/src/components/ChatProfileMediaSection.tsx`
- `mobile/src/db/`

## Как это лучше встроить

### Не напрямую из UI

Нельзя, чтобы экран чата сам "думал" про индекс.

Лучше так:

1. локальная история пишет новые сообщения в SQLite;
2. search/index layer получает изменения;
3. UI только вызывает:
   - `searchMessages(chatId, query)`
   - `getLinks(chatId)`
   - `getFiles(chatId)`

### Где Rust особенно полезен

- быстрые проходы по большим локальным наборам;
- компактный индекс;
- меньше тяжелых вычислений на JS-потоке.

## Что это даст проекту

1. Более быстрый in-chat search
2. Более масштабируемые derived tabs
3. Хорошую основу под большие локальные чаты

## Риски

- начать строить search engine слишком рано;
- продублировать то, что SQLite уже решает достаточно хорошо;
- не определить, какой объем истории реально ожидается.

## Критерий завершения

Шаг завершен, когда:

- есть отдельный Rust indexing/search core;
- mobile search и derived views могут опираться на него;
- UI не несет на себе тяжелую индексную логику.
