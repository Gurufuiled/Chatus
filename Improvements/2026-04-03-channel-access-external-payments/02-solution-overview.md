# Solution Overview

## Выбранная модель

Текущая продуктовая схема выглядит так:

1. У пользователя есть тариф аккаунта.
2. Этот тариф определяет, может ли он создавать группы и каналы.
3. Автор канала принимает деньги во внешнем сервисе.
4. Приложение не делает payouts и не считает creator revenue.
5. Приложение хранит и проверяет список разрешенных участников.
6. При потере доступа участника можно исключить.

## Роли в системе

### Обычный пользователь

Может:

- общаться;
- пользоваться чатами.

Не может:

- создавать свои платные группы/каналы, если нет нужного account plan.

### Пользователь с account plan

Может:

- создавать группы;
- создавать каналы/паблики;
- управлять доступом в свои каналы.

### Участник канала

Может:

- находиться в канале, если он есть в разрешенном списке;
- быть исключенным, если доступ больше не подтвержден.

### Владелец канала

Может:

- вести внешний прием оплаты;
- добавлять или синхронизировать список разрешенных участников;
- исключать пользователей из канала.

## Где используется `ЮKassa`

На текущем этапе `ЮKassa` фиксируется как предпочтительный внешний payment service.

Ее роль:

- внешний прием оплаты;
- внешний checkout;
- потенциальный источник webhook/API-событий;
- внешний источник подтверждения платежа.

## Что делает приложение

Приложение отвечает за:

- account plan permissions;
- каналы;
- участников;
- allowlist;
- доступ;
- исключение пользователя.

## Что приложение не делает

Приложение не отвечает за:

- внутренний расчет creator earnings;
- split payments;
- выплаты автору;
- внутреннюю подписочную бухгалтерию;
- marketplace-комиссии.

## Базовый сценарий

1. Пользователь получает нужный тариф аккаунта.
2. Пользователь создает свой канал.
3. Владелец канала принимает оплату во внешнем сервисе.
4. После оплаты пользователь попадает в allowlist канала.
5. Приложение разрешает ему находиться в канале.
6. Если внешний доступ закончился, владелец или API снимает разрешение.
7. Пользователь исключается из канала или теряет доступ к нему.
