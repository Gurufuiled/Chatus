# Technical Architecture

## Контекст

Текущая техническая архитектура должна поддерживать более простой сценарий, чем раньше:

- без внутреннего channel billing;
- без creator payout;
- без ledger и финансовой платформы.

Главный фокус теперь:

- account plan permissions;
- каналы;
- allowlist участников;
- внешний payment verification;
- управление доступом.

## Главные домены

### 1. Account Plans

Отвечает за:

- есть ли у пользователя право создавать группы;
- есть ли у пользователя право создавать каналы;
- какой у него тариф аккаунта.

### 2. Channels

Отвечает за:

- создание канала;
- настройки канала;
- публичность/приватность;
- участников;
- инвайты;
- список разрешенных участников.

### 3. External Access Control

Отвечает за:

- активен ли доступ пользователя к каналу;
- откуда этот доступ пришел;
- когда он заканчивается;
- можно ли пользователя исключить.

### 4. External Payment Integration

Отвечает за:

- связь с `ЮKassa`;
- подтверждение внешнего платежа;
- синхронизацию allowlist.

## Главный архитектурный принцип

Платеж и доступ связаны, но не одинаковы.

Нам не нужно строить сложную внутреннюю финансовую систему.
Нам нужно построить надежную систему:

- кто имеет право создать канал;
- кто имеет право быть внутри канала.

## Источник истины

### По созданию канала

Источник истины:

- account plan пользователя.

### По доступу в канал

Источник истины:

- allowlist / access grant на сервере.

Не UI и не локальное состояние.

## Как должна работать проверка доступа

При открытии канала сервер должен проверять:

- существует ли канал;
- публичный он или приватный;
- есть ли у пользователя право быть в канале;
- активен ли access grant;
- не был ли доступ отозван.

Сервер возвращает одно из состояний:

- `allowed`
- `blocked_requires_external_payment`
- `blocked_not_in_allowlist`
- `blocked_revoked`

## Как должен работать внешний платежный слой

В первой версии есть 3 допустимые модели:

1. ручная выдача доступа после оплаты;
2. полуавтоматическая выдача через админку;
3. автоматическая выдача через API/webhook от `ЮKassa`.

Самая реалистичная стартовая версия:

- allowlist как основной механизм;
- возможность позже подключить webhook без смены домена.

## Что не должно попадать в эту архитектуру

- creator balances;
- payout requests;
- payout history;
- billing ledger;
- internal revenue sharing.

Это уже другая система и сейчас она не нужна.
