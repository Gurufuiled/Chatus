# Планирование: UI Telegram-чата внутри Chatus (паритет с нативным чатом)

**Трек:** клиент `mobile/` — **`TelegramChatScreen`**, **`TelegramDialogsScreen`**, TDLib, переиспользование компонентов Chatus где возможно.  
**Связано:** единый список чатов ([unified-inbox-chatus-telegram.md](./unified-inbox-chatus-telegram.md)); на сервер Chatus это **не** опирается.

---

## Типы Telegram-чатов в области задачи

Помимо личек, в TDLib приходят **группы** (`basicGroup`, `supergroup`) и **каналы** (`channel`). Для них другие правила: кто может писать, как выглядят посты (просмотры, подпись канала), есть ли **обсуждение** (linked discussion), счётчики участников. Это должно быть отражено и в **списке диалогов**, и в **экране чата**, и в **композере** — см. **фазы F и G** (каналы/группы и затем визуальное выравнивание с Chatus).

---

## Проблема (текущее состояние)

В Telegram-ветке чаты выглядят как **минимальный прототип**:

- У исходящих сообщений **нет полноценных индикаторов доставки/прочтения** в стиле Telegram (одна галочка / две / время прочтения). В коде строка меты для текста — это время и только `· ...` при отправке и `· !` при ошибке; для успешно отправленных статус не отражает цепочку TDLib.
- **`mapTdMessage`** в `TelegramChatScreen.tsx` всегда ставит исходящим `status: 'sent'` и не читает из объекта сообщения TDLib поля вроде состояния отправки, доставки, просмотра.
- Подписка на апдейты ограничена `updateNewMessage` и `updateMessageSendSucceeded` — нет обработки обновлений, которые меняют **read/delivery** у уже показанных сообщений.
- **Голосовые:** переиспользуется `VoiceBubble`, но без данных TDLib о waveform из файла часто пустой массив; UX уже лучше заглушки, но нет выравнивания с тем, как устроен нативный чат Chatus (реакции, статусы в одном стиле).
- **`InputBar`** подключён с подсказкой `mediaRestriction` — явно отрезаны вложения, фото, видео и прочие действия, которые в обычном чате Chatus есть.
- Типы контента кроме `messageText` и `messageVoiceNote` сводятся к строке-заглушке («Фото», «Файл»…), без превью и открытия.

Итог для пользователя: «вижу текст, время, могу отправить текст и голос; остальное как будто не приложение».

**Каналы и группы** сейчас не выделены отдельным UX: список диалогов (`TelegramDialogsScreen`) по сути общий для всех типов чатов без бейджей «канал / группа / N участников»; экран **`TelegramChatScreen`** не учитывает `chat.type` из **`getChat`** — композер и заголовок одинаковы для лички и канала, нет поведения «только чтение» для подписчика канала, нет просмотров постов и типичной шапки канала/супергруппы.

---

## Цель планирования

1. Зафиксировать **матрицу возможностей TDLib** vs **UX нативного `ChatScreen` / компонентов Chatus**.  
2. Разбить работу на **фазы**, чтобы не ломать TDLib-авторизацию и историю одним огромным PR.  
3. Определить, что **переиспользуем** (`VoiceBubble`, `InputBar`, паттерны времени/статуса из `MessageTimeStatus`), а что **остаётся tg-специфичным** (ID сообщений, `sendMessage` с другими `input_message_content`).

## Фазы внедрения (рекомендуемый порядок)

### Фаза A — Статусы исходящих и синх с TDLib

**Цель:** исходящие сообщения отражают реальное состояние: отправка, ошибка, доставлено, прочитано (в разумных пределах API TDLib).

- Разобрать поля сообщения TDLib для исходящих: `sending_state`, события обновления сообщения при смене статуса.
- Подписаться на апдейты, которые обновляют уже отображённые сообщения (не только `updateNewMessage` / `updateMessageSendSucceeded`).
- Свести к единому типу статуса для `MessageTimeStatus` / текстового ряда (как в нативном чате — см. существующие значения).
- **Результат:** визуально понятно «летит / не ушло / доставлено / прочитано» без полного клонирования Telegram.

### Фаза B — Композер (InputBar): по шагам те же возможности, что доступны TDLib

**Цель:** не одна строка «только текст и голос», а поэтапное включение: вложения файлов, фото/видео с камеры или галереи, если покрывается `inputMessage*` TDLib и UX согласован.

- Инвентаризация: какие кнопки есть у нативного `InputBar` в режиме Chatus и какие из них имеют прямой аналог в TDLib.
- Для каждой кнопки: либо реализация, либо явное «пока скрыто» с тем же layout, что нативный чат (чтобы не было «пустого» композера).

### Фаза C — Отображение входящих типов контента

**Цель:** не только заглушка «Фото» / «Файл», а превью и открытие там, где это целесообразно.

- `messagePhoto`, `messageVideo`, `messageDocument`, стикеры — отдельные строки UI или переиспользование компонентов из нативного чата (если данные приводятся к тем же пропсам).
- Загрузка файлов через уже используемый `downloadFile`, кэш путей.

### Фаза D — Паритет «социальных» фич чата

**Цель:** ответ на сообщение, пересылка, редактирование (если TDLib и продукт позволяют), реакции — по приоритету продукта.

- Многое завязано на **long-press меню** и навигацию; можно переиспользовать паттерны из нативного чата.

### Фаза E — Полировка визуала

Группировка подряд идущих сообщений от одного автора, аватарки в цепочке (опционально), отступы из `telegramChatUi.ts`, тёмная тема, доступность.

### Фаза F — Каналы и групповые чаты (UI/UX)

**Цель:** каналы и группы **выглядят и ведут себя** как ожидается в Telegram-подобном клиенте, в одном стиле с остальным Chatus после фаз A–E (не «все чаты как личка»).

**Список чатов**

- Определить из TDLib тип каждого диалога (канал / группа / секрет / личка) и показать **визуальную метку** или вторую строку (название канала, «N участников», verified при наличии данных).
- Различать превью последнего сообщения для каналов (посты, альбомы) тем же языком, что и после фазы C.

**Шапка экрана чата**

- Для **канала:** название, статус подписчика / число подписчиков (если доступно из API), аватар; действия «инфо о канале» по аналогии с эталоном Chatus (отдельный экран или bottom sheet — по приоритету).
- Для **группы / супергруппы:** название, число участников, при необходимости тип (группа / супергруппа).

**Лента сообщений**

- **Канал:** для постов — отображение **просмотров** (`view_count` в TDLib для сообщений канала), корректное различие поста и комментария, если вводится связка с discussion (может быть отдельной подфазой).
- **Группа:** при необходимости имя отправителя на каждом пузыре в больших группах (как в Telegram), чтобы не смешивать авторов.

**Композер**

- **Канал:** если пользователь **не может** постить — скрыть или заменить поле ввода на явное состояние «только чтение» / кнопку админских действий; если может (админ) — включить отправку через TDLib с теми же статусами, что фаза A.
- **Группа:** полный композер по мере реализации фазы B (вложения, упоминания при наличии API).

**Навигация**

- Перейти к **обсуждению** поста канала (linked discussion chat), если продукт это включает — отдельная связка маршрутов и экранов.

- **Результат:** пользователь визуально отличает канал от группы и от лички; не видит «сломанный» композер в канале-only режиме; групповые чаты читаемы при нескольких участниках.

### Фаза G — Шапка, профиль, обои и цвета (единство с Chatus)

**Цель:** после функциональных фаз A–F Telegram-чат **выглядит частью одного приложения**, а не отдельным серым прототипом: те же принципы, что у нативного `ChatScreen` и настроек оформления. Дополняет **фазу E** (отступы/группировка в ленте): здесь — шапка, фон, палитра пузырей и согласованность с настройками Chatus.

**Шапка экрана и профиль**

- Полноценная **шапка чата** (не только hint-текст): аватар, заголовок, подпись (статус / username / число участников — по типу чата и TDLib).
- Действие «открыть профиль / информацию о чате» — по паттерну нативного чата (экран или bottom sheet), без обязательства клонировать Telegram Official pixel-perfect.

**Фон и обои**

- Фон ленты сообщений использует **те же настройки обоев / фона чата**, что и остальной мессенджер Chatus (где в приложении они уже задаются — переиспользовать store/context; если для TG-ветки отдельный флаг — явно задокументировать и синхронизировать с UX «одно приложение»).

**Пузыри и акценты**

- Цвета **исходящих / входящих** баблов, разделителей и вторичного текста выровнять с **`ThemeContext`** и токенами нативного чата (`bubbleMe`, `bubbleOther`, мета-время и т.д.), чтобы не было «другого набора цветов только для Telegram».

**Клавиатура и поле ввода (мелкие, но критичные детали)**

- Везде, где есть **бабл/панель ввода текста** (`InputBar` и аналоги на экранах Telegram): при открытии клавиатуры композер **остаётся над клавиатурой**, вводимый текст **виден** (не уезжает под системную клавиатуру). Ориентир — поведение нативного `ChatScreen`: `KeyboardAvoidingView` / актуальный подход к клавиатуре в RN, при необходимости `keyboardVerticalOffset`, на Android согласование с `windowSoftInputMode` / adjustResize.
- Отдельная проверка на **Android и iOS**, разные высоты клавиатуры и переключение языка.

**Системная навигация и safe area**

- Учёт **safe area** и отступов снизу: **home indicator** (iOS), **жестовая панель** и **трёхкнопочная навигация** (Android) дают разный нижний inset — композер и список не должны «плавать» или перекрываться.
- Смоук: хотя бы один прогон на профиле с **жестами** и с **кнопками** (настройки системы Android), чтобы убедиться, что ввод и таб-бар не конфликтуют.
- При использовании **react-native-gesture-handler** / swipe-back — убедиться, что жесты не перехватывают ввод и скролл ленты без намерения.

**Регресс**

- Не ломать тёмную тему и доступность; после G пройти быстрый чеклист «личка / группа / канал» на светлой и тёмной теме.

- **Результат:** пользователь не ощущает Telegram-ветку визуально «чужой» по отношению к Chatus; шапка и фон не выглядят временными заглушками.

---

## Вне скоупа этой задачи (или отдельный эпик)

- Полное визуальное совпадение с **официальным клиентом Telegram** (не цель; цель — **не хуже эталона Chatus** внутри приложения).
- Функции, которых **нет в TDLib** для пользовательских ботов/mini-apps в том виде, как в Chatus-сервере — отдельное ТЗ.
- Серверный relay/P2P (`docs/p2p/`) — не блокирует и не заменяет эту дорожку.
- **Полный набор** админских сценариев канала (статистика, редактирование всех постов) — только если явно войдёт в продукт; базово достаточно читателя и простого постинга для прав.

## Критерии приёмки (верхний уровень)

- [ ] Исходящие сообщения показывают осмысленные статусы, согласованные с TDLib и с UI нативного чата Chatus (галочки/время чтения — по возможности API).
- [ ] Композер не выглядит как «урезанный навсегда»: либо включены функции, либо явные ограничения убраны с главной плоскости после реализации фазы B.
- [ ] Основные типы входящих медиа открываются или показывают превью, а не одну строку «Фото».
- [ ] **Каналы и группы:** в списке диалогов различимы тип и ключевые метаданные; в чате — корректная шапка; композер соответствует правам (канал read-only vs постинг); групповые сообщения читаемы; для постов канала отображаются просмотры там, где поддерживает TDLib.
- [ ] **Фаза G:** шапка чата и переход к профилю/инфо не выглядят заглушкой; фон/обои и цвета пузырей согласованы с темой и настройками Chatus (светлая/тёмная тема); **поле ввода при открытой клавиатуре остаётся видимым над клавиатурой**; проверены **safe area** и навигация Android (**жесты / три кнопки**).
- [ ] Регресс: авторизация TG, история, отправка текста и голоса в личке не сломаны.

## Порядок фаз (уточнение)

Личка и общие механики обычно идут **A → E**; **F** логично начинать после **A + C** минимум (статусы и типы контента), чтобы каналы не выглядели «богато» в списке и «пусто» в ленте. Часть пунктов F (бейджи в списке) можно делать параллельно с B.

**Фаза G** — отдельный финишный слой **после F** (или параллельно концу F, если разные люди): визуальное и тематическое выравнивание, **клавиатура + safe area**, проверка под разные режимы системной навигации — без этого интерфейс TG-ветки остаётся «функциональным, но чужим» или неудобным при вводе.

## Статус

Документ задаёт **этап планирования**; конкретные оценки и порядок фаз **A→G** можно уточнить после короткого спайка по TDLib (`getChat`, типы контента, права в канале) и списку фич нативного `ChatScreen`.
