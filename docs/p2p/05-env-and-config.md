# Переменные окружения и конфиг (черновик для relay / кэша)

Этот файл фиксирует имена и смысл переменных для фазы «политика доставки и хранения». Реализованный поднабор читается через единый модуль конфигурации NestJS (`RelayPolicyConfig`), а будущие переменные стоит добавлять туда же, не разбрасывая `process.env` по сервисам.

**Область:** переменные `RELAY_*` относятся к **сообщениям и файлам на сервере Chatus**. Доставка и хранилище **Telegram** ими не управляются; см. [06-unified-inbox-telegram-scope.md](./06-unified-inbox-telegram-scope.md).

**Единицы времени:** секунды (`_SECONDS`), если не указано иное. Для «отключить TTL» часто используют `0` или пустое значение — конкретную семантику зафиксировать в коде один раз.

## Уже существующие переменные сервера (справочно)

Имеют отношение к сети и медиа, но **не** к политике P2P/relay:

| Переменная | Назначение |
|------------|------------|
| `PORT` | HTTP API (по умолчанию 4000). |
| `WS_PORT` | WebSocket чата (по умолчанию 4001). |

| `RUST_MEDIA_WORKER_ENABLED`, `RUST_MEDIA_WORKER_BIN`, `RUST_MEDIA_WORKER_TIMEOUT_MS` | Опциональный воркер обработки медиа. |

## Черновик: общая политика «mailbox / relay»

Идея — управлять тем, **как долго** сервер держит данные после того, как получатель мог их забрать, и нужно ли **удалять blob** медиа с диска.

| Переменная | Тип | Пример | Смысл |
|------------|-----|--------|--------|
| `RELAY_TEXT_CACHE_SECONDS` | int | `86400` | Сколько сервер **гарантированно** держит текстовое тело / метаданные сообщения для повторной выдачи (новое устройство, повторный sync). `0` — не истечение по времени (или отдельное значение «навсегда до удаления» — явно описать в коде). |
| `RELAY_DELETE_AFTER_ALL_DEVICES_ACK` | `0` \| `1` | `0` | Если `1`: после подтверждения доставки/прочтения **всеми** сессиями пользователя — можно удалять серверную копию текста (POP-подобно). Требует учёт мультидевайса. |
| `RELAY_MODE` | string | `standard` | Заготовка под профили: `standard` (долгий кэш), `minimal` (короткий TTL), `pop_like` (агрессивное удаление). Реализация может маппить профиль в набор TTL без десятка отдельных env. |

---

## Черновик: медиа (файлы на диске / object storage)

Отдельно от текста: медиа дороже и чаще ограничивают по размеру и сроку.

| Переменная | Тип | Пример | Смысл |
|------------|-----|--------|--------|
| `RELAY_MEDIA_CACHE_SECONDS` | int | `604800` | Время, после которого **можно** удалить загруженный файл с сервера, если выполнены условия политики (например все получатели скачали или прошёл срок). |
| `RELAY_MEDIA_RETAIN_UNTIL_DOWNLOAD` | `0` \| `1` | `1` | Пока хотя бы один получатель не подтвердил загрузку / не истёк grace-период — не удалять blob. |
| `RELAY_MEDIA_MAX_BYTES` | int | — | Верхняя граница размера одного upload для relay-режима (может дублировать лимит nginx/body parser — лучше один источник истины). |

Уточнение по типам (опционально, если решите дробить политику):

- `RELAY_MEDIA_CACHE_SECONDS_IMAGE`
- `RELAY_MEDIA_CACHE_SECONDS_VIDEO`
- `RELAY_MEDIA_CACHE_SECONDS_VOICE`
- `RELAY_MEDIA_CACHE_SECONDS_FILE`

Имеет смысл добавлять только если продукт реально задаёт разные сроки; иначе достаточно одного `RELAY_MEDIA_CACHE_SECONDS`.

## Клиент: конфиг по умолчанию

На мобильном клиенте обычно **не** дублируют все серверные TTL; достаточно:

- соответствие **`transport`** и флагов «сообщение получено с сервера» vs «ожидаем peer» (когда появится);
- локальные лимиты кэша изображений/видео в файловой системе (Expo/React Native) — по необходимости отдельные ключи в **своём** конфиге приложения, не обязательно через env в релизе.

Если понадобится выставлять поведение без релиза сервера: **remote config** или endpoint «политика клиента» — вынести в отдельную задачу, не смешивать с `.env` сервера.

## Рекомендации по внедрению в коде

1. Один **prefix** (`RELAY_*` или `CHATUS_CACHE_*`) — чтобы в `.env` было видно группу переменных.
2. Парсинг в `main.ts` или `ConfigModule`: числа через `parseInt(..., 10)`, булевы через явное сравнение с `'1'` / `'true'`.
3. Значения по умолчанию должны совпадать с текущим поведением («храним как сейчас»), пока фича не включена явно.
4. Документировать в README деплоя только те переменные, которые реально прочитаны в текущей версии образа.

После появления первой реализации этот файл стоит сопоставить с фактическим `ConfigService` или `.env.example` в `server/`.

## Реализация фазы 0

На сервере добавлен `RelayPolicyConfig` (`server/src/config/relay-policy.config.ts`) и подключён к `MessagesService`. В текущей фазе конфиг только фиксирует политику и дефолтный транспорт:

- `defaultTransport = websocket`;
- `RELAY_TEXT_CACHE_SECONDS=0` и `RELAY_MEDIA_CACHE_SECONDS=0` означают отсутствие TTL-удаления;
- POP-подобное удаление (`RELAY_DELETE_AFTER_ALL_DEVICES_ACK=1`) только читается как флаг будущей фазы, без изменения доставки;
- переменные относятся только к нативным сообщениям Chatus.
