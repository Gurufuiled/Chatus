# Единый список чатов: Chatus + привязанный Telegram

Продуктовое направление (без кода в этом документе): пользователь **логинится в Chatus**, затем в **настройках привязывает аккаунт Telegram**; в основном списке **смешиваются** чаты Chatus и чаты Telegram — **без** переключателя режима инбокса, который использовался ранее в идее «Loginus vs Telegram».

Этот документ фиксирует, **что меняется в планах P2P/relay**, а что остаётся прежним.

---

## Область действия документов `docs/p2p/`

Все фазы ([03-rollout-phases.md](./03-rollout-phases.md)), политики кэша ([05-env-and-config.md](./05-env-and-config.md)) и типы сообщений ([04-message-types-and-media.md](./04-message-types-and-media.md)) относятся **только к нативному контуру Chatus**:

- сервер NestJS, PostgreSQL, Prisma `Message` / `Transport`;
- WebSocket чата (`send_message`, `RealtimeService`);
- клиентский SQLite, `TransportService`, `SyncService`, `sync_queue`.

**Telegram** после привязки продолжает жить на **инфраструктуре Telegram** (TDLib / MTProto): доставка, хранение истории, медиа и ограничения — по правилам Telegram, не по нашим `RELAY_*` и не по нашему серверному mailbox.

Итого: **единый UI списка чатов не объединяет транспорт на уровне протокола.** Это два источника данных в одном экране.

---

## Что в планах P2P **не** нужно переписывать из‑за единого инбокса

- Модель relay/TTL на **нашем** сервере остаётся про **сообщения Chatus**.
- Отдельная политика «удалить медиа с нашего диска через N секунд» **не применяется** к файлам, которые Telegram отдаёт со своих CDN по своим URL.

Менять имеет смысл только **клиентскую композицию** (как строится список, сортировка, бейджи, навигация в нужный стек экранов). Это **параллельный трек** к работам из `docs/p2p/`, не замена фаз.

## Что иметь в виду при проектировании (пересечения)

| Тема | Замечание |
|------|-----------|
| **Идентификаторы чатов** | У Chatus и Telegram разные пространства ID. В объединённом списке у каждой строки нужен явный **источник** (`chatus` \| `telegram`) или эквивалент, чтобы не смешивать маршрутизацию и БД. |
| **Офлайн** | Очередь `sync_queue` и P2P-планирование относятся к **исходящим нативным** сообщениям. Исходящие в Telegram идут через TDLib — свои очереди и состояния. |
| **Медиа** | Для Chatus — upload на наш API и `remote_url` в SQLite. Для TG — кэш TDLib / локальные пути своей модели. Общий «blob retention» на сервере Chatus на TG не влияет. |
| **Звонки / signaling** | Уже разведены концептуально: signaling 4002 для WebRTC Chatus. Звонки Telegram — другой контур, если появятся. |
| **«Мультидевайс» в фазах P2P** | Речь про **несколько устройств одного пользователя Chatus** и синхронизацию с нашим backend. Привязка Telegram — это **подключение другого аккаунта/сети**, не замена этой фазы. |

## Связь с текущей реализацией в приложении

Сейчас в коде есть разделение режима инбокса (`inboxModeStore`: `loginus` \| `telegram`) и учёт Telegram-аккаунта (`telegramAccountStore`). Переход к **одному списку без переключателя** — продуктово-UX решение: отказ от выбора «какой инбокс активен» в пользу **агрегированного** представления после привязки TG.

Документы в `docs/p2p/` не описывают миграцию этих сторов; спецификация и чеклист вынесены в задачу **[Единый список чатов](../tasks/unified-inbox-chatus-telegram.md)**.

## Краткий вывод для команды

- Планы **P2P / relay / кэш сервера** остаются актуальны **без пересмотра фаз** только потому, что появился единый список с Telegram.
- Нужно **явно различать** в спецификациях и коде: политики **Chatus server** vs поведение **Telegram API**.
- Если позже понадобится «общая» метрика доставки или сквозной архив — это **отдельный эпик**, не подмешивается в текущие фазы P2P автоматически.
