# Термины и принципы

## Целевая модель продукта: P2P-first

**Главная задумка Chatus (нативный контур):**

1. **Сначала** доставка **напрямую между клиентами** (peer-to-peer / peer-assisted канал — например WebRTC Data Channel после договорённости через signaling), когда это возможно.
2. **Если peer-путь недоступен или недостаточен** (получатель офлайн, не удалось установить соединение, таймаут, NAT и т.д.) — сообщение **уходит на сервер** во **временное хранилище / mailbox**, откуда получатель забирает его при появлении в сети; дальше действуют политики **TTL / удаление после забора** (`RELAY_*`, см. [05-env-and-config.md](./05-env-and-config.md)).

Сервер при этом **не обязан** быть первым hop для каждого сообщения в личке 1:1 в целевой архитектуре. Его роли:

- **Учёт и безопасность:** аутентификация, членство в чатах, ACL.
- **Mailbox / запасной канал:** хранение только того, что **не удалось** или **не должно** пройти напрямую через peer в данный момент.
- **Точка согласования:** signaling для установки peer-сессии (отдельно от медиа звонков при необходимости расширения).
- **Якорь для сложных сценариев:** группы, каналы, история на новом устройстве — там полный отказ от сервера часто нереалистичен; см. ниже.

**Текущий код** до внедрения по-прежнему **server-first** (всё через WebSocket в БД). Переход к P2P-first — содержание фаз в [03-rollout-phases.md](./03-rollout-phases.md).

## Как называть модель в продукте

- **P2P-first** — приоритет прямой доставки; сервер как буфер и фолбэк (официальная формулировка цели).
- **Гибридная доставка** — peer + сервер в связке; сервер не обязан быть «главной шиной» для каждого сообщения в личке.
- **Mailbox / relay** — то, что лежит на сервере **после фолбэка** или по политике (TTL, POP-подобное удаление после забора).

## Роли компонентов (целевое состояние после внедрения)

| Роль | Назначение |
|------|------------|
| **Сервер (NestJS)** | Аутентификация, членство в чатах, **mailbox** для сообщений без успешного peer, загрузки при необходимости, fan-out там, где peer не масштабируется (группы/каналы), push, Prisma enum **`Transport`**. |
| **Peer-слой (клиент)** | Попытка установить прямую доставку 1:1; при успехе — **`transport: p2p`** без полной записи «как сейчас» для каждого шага (конкретная схема учёта — в фазах реализации). |
| **WebSocket чата** (`WS_PORT`, обычно 4001) | Доставка через сервер, статусы, fallback-сценарии, синхронизация с теми, кто не на peer-пути. |
| **Signaling WebSocket** (4002) | Сейчас **звонки** WebRTC; для **сообщений чата** может использоваться расширенно (SDP/ICE для Data Channel) — отдельные задачи в фазах, не смешивать с голосовым звонком без проектирования. |
| **Клиент SQLite** | Офлайн-first: локальная очередь до успешной отправки (peer или сервер), хранение сообщений и медиа. |
| **Транспорт сообщения** | На сервере: `Message.transport` ∈ `{ websocket, p2p }`. **`p2p`** — сообщение доставлено/учтено как прошедшее через peer-путь; **`websocket`** — через серверный relay/mailbox. На клиенте выровнять именование с API. |

## Два бэкенда в одном приложении (Chatus + Telegram)

В продукте возможен **единый экран списка чатов**, где рядом показываются диалоги **Chatus** и **Telegram**. Это **не** объединяет транспорт: Telegram остаётся на TDLib. Документы в этой папке про P2P-first относятся **только к Chatus**. Подробнее: [06-unified-inbox-telegram-scope.md](./06-unified-inbox-telegram-scope.md).

## Разделение «текст / метаданные» и «медиа-блобы»

- При **peer-first** текст и мелкие метаданные могут уйти напрямую; крупные файлы часто требуют **либо** прямой передачи peer, **либо** указателя + загрузка на сервер при фолбэке (см. [04-message-types-and-media.md](./04-message-types-and-media.md)).
- **Бинарные файлы** — дорого держать на сервере для всех; политики `RELAY_MEDIA_*` задают поведение **когда blob попал на сервер** (фолбэк или обязательный upload по типу чата).

## Каналы и группы

- **Приватный чат 1:1** — основной объект для **P2P-first**.
- **Группа / канал** — как правило **серверный fan-out и хранение** остаются необходимыми для UX «как в Telegram»; peer там может быть только дополнительным механизмом, не заменой центральной записи для всех участников.

## Нефункциональные требования

- **Согласованность имён**: Prisma `Transport`, REST/WebSocket payload, SQLite `messages.transport`.
- **Обратная совместимость** при поэтапном rollout: старые клиенты могут оставаться server-only до обновления.
- **Наблюдаемость:** метрики попыток peer vs fallback на сервер — желательно для отладки NAT и политик mailbox.
