# Термины и принципы

## Как называть модель в продукте

Рекомендуется избегать одного слова «P2P» без уточнения. Варианты формулировок:

- **Гибридная доставка** — сервер участвует всегда или почти всегда.
- **Peer-assisted sync** — второе устройство или контакт помогает дополнить историю, но не единственный источник истины.
- **Server relay + клиентский кэш** — соответствует обсуждению «cache relay», настраиваемый TTL, POP-подобное удаление после забора.

## Роли компонентов

| Роль | Назначение |
|------|------------|
| **Сервер (NestJS)** | Аутентификация, членство в чатах, запись сообщений в PostgreSQL, fan-out по WebSocket (`RealtimeService`), push, загрузки статики (`/uploads`), Prisma enum **`Transport`**. |
| **WebSocket чата** (`WS_PORT`, обычно 4001) | События `send_message`, broadcast участникам чата после `MessagesService.createMessage`. |
| **Signaling WebSocket** (4002) | Сейчас **только звонки** WebRTC (`SignalingService` / `SignalingGateway`), не перенос сообщений чата. Любой перенос данных чата по WebRTC data channel — **отдельное решение и отдельная фаза**. |
| **Клиент SQLite** | Офлайн-first: `messages`, `media` (`local_path` / `remote_url`), очередь `sync_queue`, действия вида `send_message_*` в `SyncService`. |
| **Транспорт сообщения** | На сервере: `Message.transport` ∈ `{ websocket, p2p }`. На клиенте сейчас: строка `transport` по умолчанию **`server`** — нужно выровнять с контрактом API при внедрении. |

## Два бэкенда в одном приложении (Chatus + Telegram)

В продукте возможен **единый экран списка чатов**, где рядом показываются диалоги **Chatus** (наш сервер) и **Telegram** (после привязки аккаунта в настройках). Это **не** объединяет транспорт на уровне протокола: Telegram по-прежнему использует TDLib и инфраструктуру Telegram. Документы в этой папке про relay/P2P относятся **только к Chatus**. Подробнее: [06-unified-inbox-telegram-scope.md](./06-unified-inbox-telegram-scope.md).

## Разделение «текст / метаданные» и «медиа-блобы»

- **Текст и метаданные** (тип сообщения, ссылки на медиа, размеры, waveform как JSON в БД сервера) — относительно дёшево хранить на сервере и дублировать в ответах API.
- **Бинарные файлы** (изображения, голос, video note, видео, документы) — дорого размножать по всем «пирам»; типичные стратегии:
  - только **URL на объект** после загрузки на сервер (текущая модель);
  - **TTL-кэш** на сервере с настройкой;
  - **указатель на отправителя** + загрузка при онлайне (жёсткий UX, опциональный режим).

Это напрямую влияет на план фаз: сначала политики и метаданные, затем поведение загрузок (`apiUpload`, `apiUploadVoice`) и очереди синхронизации.

## Каналы и группы

- **Приватный чат 1:1** — минимальный набор для первых итераций.
- **Группа** — fan-out по членам чата уже есть на сервере; меняется только политика хранения и возможный peer-assist.
- **Канал** — публикации как `Message` с `is_channel_post`; нужна явная политика **retention** и **доставки новым подписчикам** (без «магии чистого P2P» для широкой аудитории).

## Нефункциональные требования

- **Согласованность имён**: Prisma `Transport`, REST/WebSocket payload, SQLite `messages.transport`.
- **Обратная совместимость**: старые клиенты должны продолжать работать с `transport = websocket` / эквивалентом `server`.
- **Наблюдаемость**: логирование на сервере есть точечно; отдельный дашборд — по желанию фазы, не блокер для протокола.
