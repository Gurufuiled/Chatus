# Типы сообщений и медиа: где встраивать P2P-first и fallback

Соответствие типам в Prisma / клиенте: `text`, `image`, `voice`, `video_note`, `video`, `file`, `system` (system обычно только через сервер).

**Цель:** в **личке 1:1** по возможности передавать контент по **peer**; при фолбэке — текущий путь через сервер (upload + `send_message`). Ниже для каждого типа: **текущий путь**, **что менять**, **риски**.

---

## Общие столбцы таблицы

| Тип | Ключевые методы клиента | Поля `media` / контента | Сервер: `MediaType` |
|-----|-------------------------|-------------------------|---------------------|
| text | `sendTextMessage`, очередь `send_message_text` | `content` | нет медиа |
| image | `sendImageMessage`, `send_message_image` | `url`, `thumbnail_url`, размеры | `image` |
| voice | `sendVoiceMessage`, `send_message_voice` | `url`, `duration_ms`, `waveform` | `voice` |
| video_note | `sendVideoNoteMessage`, `send_message_video_note` | `url`, `thumbnail_url`, `is_round`, `duration_ms` | `video_note` |
| video | `sendVideoMessage`, `send_message_video` | `url`, `thumbnail_url`, размеры, длительность | `video` |
| file | `sendFileMessage`, `send_message_file` | `url`, `file_name`, `file_size` | `file` |
| альбомы | отдельные ветки в `TransportService` / `SyncService` | несколько вложений | несколько `Media` |

---

## Текст (`text`)

- **Поток:** `WebSocketService.sendEvent('send_message', { msg_type: 'text', … })` или очередь.
- **Встраивание:** минимальное; основной объект политик TTL на сервере и удаления «после прочтения».
- **P2P-метаданные:** достаточно поля `transport` и версии протокола в payload при необходимости.

---

## Изображение (`image`)

- **Поток:** HTTP upload → в сообщении полный URL → peers получают тот же URL.
- **Встраивание:**
  - Политика **как долго** файл доступен по URL на сервере (статика / CDN).
  - Клиент: кэш на диске уже через `media.local_path`; при «истечении» сервера — показывать placeholder и инициировать peer-assist (если когда-либо появится).
- **Риск:** большие альбомы и повторная отправка — следить за дублями в `sync_queue`.

---

## Голос (`voice`)

- **Поток:** часто `apiUploadVoice`; в сообщении `media.url` + `waveform`.
- **Встраивание:** то же, что для файлов; waveform хранится на сервере в `Media` (байты).
- **Риск офлайна:** очередь `send_message_voice` должна сохранять локальный URI до успешной загрузки (уже учитывается в текущем дизайне очереди).

---

## Видео-кружок (`video_note`)

- **Поток:** upload + `is_round: true`, превью `thumbnail_url`.
- **Встраивание:** как видео/изображение; UX «кружка» не меняется при смене транспорта.
- **Риск:** превью и основной файл — два артефакта; политика TTL может различать их (редко нужно на первом этапе).

---

## Видео (`video`)

- **Поток:** тяжёлый upload; те же точки, что image + лимиты размера.
- **Встраивание:** обязательно учитывать **413** и backoff в `TransportService`; для гибрида — приоритет серверного кэша длиннее, чем для текста.

---

## Файл (`file`)

- **Поток:** upload с именем и размером; в тексте сообщения может отображаться имя (`getSafeFileContent`).
- **Встраивание:** контроль квот и sanitization имён файла; политика «только метаданные в relay, blob по запросу».

---

## Каналы: посты с медиа

- Типы те же (`createChannelPost`), но audience — подписчики.
- **Встраивание:** не в `TransportService` отдельно, а в **политике канала**: минимальный срок хранения постов и медиа, чтобы новые подписчики не видели пустоту.

---

## Очередь синхронизации (`SyncService`)

Любое новое действие «отправить позже» должно иметь **симметричный** `case` в `processSyncQueue`, иначе офлайн-сценарий сломается. При добавлении нового транспорта проверять:

- Все `send_message_*` ветки.
- Идемпотентность `entity_id` / `client_temp_id` относительно сервера.

---

## Рекомендуемый порядок реализации по типам (после фазы контракта)

1. **text** — протащить `transport` и политики без смены UX.  
2. **image + file** — URL-based, проще всего для TTL на сервере.  
3. **voice + video_note** — зависимость от upload и превью.  
4. **video + альбомы** — максимум краевых случаев по размеру и времени.

Этот порядок совпадает с нарастанием стоимости ошибки и сложности отката.
