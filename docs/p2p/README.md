# P2P и гибридная доставка (документация планирования)

Папка описывает **пошаговое внедрение** модели «peer-assisted / server relay» для мессенджера Chatus: как это соотносится с текущим стеком (HTTP, WebSocket чата, SQLite, загрузки медиа) и **куда именно** встраивать изменения в клиенте и на сервере.

**Единый список чатов Chatus + Telegram** (привязка TG в настройках, без переключателя инбокса) **не отменяет** эти планы: relay/TTL относятся к **нативному** контуру Chatus; Telegram остаётся на своём транспорте. Подробнее: [06-unified-inbox-telegram-scope.md](./06-unified-inbox-telegram-scope.md).

## Быстрый консенсус для команды

- **Транспорт «чистого P2P» без сервера** для всех сценариев (каналы, офлайн, медиа) с UX уровня Telegram обычно **недостижим** без постоянного слоя хранения или жёстких компромиссов.
- Реалистичная цель — **гибрид**: сервер как **очередь / кэш / индекс**, клиенты как **кэши и при необходимости источники повторной синхронизации**; опционально **дополнительный** peer-assisted канал для части данных.
- Поле **`transport`** согласовано для Chatus как **`websocket` | `p2p`**. Старые клиентские значения **`server`** / **`ws`** нормализуются в **`websocket`** при чтении и SQLite-миграции.

Дальнейшие правки этих файлов — по мере уточнения решений на созвонах; код менять не обязательно до старта соответствующей фазы.
